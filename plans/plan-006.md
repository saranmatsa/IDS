## Phase 006 — Create the ids-topology crate: Research Findings & Implementation Blueprint

**Status:** Research complete (30 targeted searches executed). No code written, no files modified. This document is the blueprint for implementation.

---

### 1. Executive Summary

Phase 006 creates a **new separate crate `ids-topology`** (not folders inside existing crates), organized into subfolders by subsystem. It models failure domains and performs correlated failure placement for the IDS distributed system: a CRUSH-style hierarchical topology map that places replicas/fragments across independent failure domains (power, facility, network, operator, geographic) so that no single correlated event can take out more than one replica of any data unit.

The crate owns the `FailureDomain` hierarchy already declared in `ids-000-aa::types.rs` and fleshes it out with topology map construction, correlated-failure modeling, placement constraints, and domain independence verification. All traffic rides `ids-carrier::Endpoint` (opaque `CarrierType` + `Vec<u8>`); no networking stack assumptions anywhere. Allowed crypto only: ed25519, xchacha20poly1305, sha256, blake3, chacha20poly1305.

**Core algorithmic choice:** A hierarchical bucket-tree placement model (CRUSH, Weil et al., SC'06 "Controlled, Scalable, Decentralized Placement of Replicated Data") where each internal bucket type corresponds to a failure-domain level (host → rack/power-domain → facility → operator → geographic region), placement rules select distinct buckets at each level, correlated-failure probability estimates weight each domain, and an independence verifier rejects any placement whose joint failure probability exceeds a threshold. Deterministic, coordinate-free, carrier-agnostic: any node can compute the placement of any data unit from the shared topology map alone — no central placement server, no directory.

The topology crate sits between `ids-000-aa` (canonical `FailureDomain` type) and `ids-placement` (capacity-aware engine that consumes topology constraints). It is a local, deterministic placement engine — not a network protocol.

**Data flow:** placement request (data unit + redundancy policy) → topology-map lookup → CRUSH-style bucket descent selecting distinct failure domains at each configured level → correlated-failure probability computed for the candidate set → independence verifier checks joint probability against threshold → accepted placement returned as `PlacementDecision` (from `ids-000-aa`); rejected placement returns a constraint-violation error. No `ids-carrier` traffic is generated by the topology crate itself — it is a pure function of the topology map + input; `ids-carrier::Endpoint` is used only when the placement result must be communicated to another node (e.g., during topology sync).

### 3. Detailed Research Dimensions

#### 3.1 CRUSH-style hierarchical placement (Weil et al., SC'06; Ceph CRUSH maps)

CRUSH (Controlled Replication Under Scalable Hashing) is a pseudo-random, deterministic data distribution algorithm that maps an input value (object ID / placement key) to a list of storage devices using only a compact hierarchical cluster map and a placement policy. Key properties directly adopted for `ids-topology`:

- **Distributed, directory-free:** any party can independently compute the location of any data unit from the shared topology map — no central directory, no per-object directory lookup. Matches the IDS no-global-master invariant and carrier-agnostic design.
- **Failure-domain aware:** the hierarchy models physical organization (host, rack, row, room, datacenter, region). Placement rules separate replicas across different failure domains so a single correlated event (shared power source, shared network switch, physical proximity) cannot take out more than one replica.
- **Deterministic rebalancing:** when devices are added/removed, only a minimal amount of data moves (proportional to the change), avoiding massive reshuffling.
- **Bucket types:** uniform, list, tree, straw2 — internal nodes in the hierarchy; leaf devices carry weights (capacity). `choose firstn` / `chooseleaf firstn` rule steps select N distinct buckets of a given type, retrying on collision; `chooseleaf` recurses into buckets to find a single leaf device.

CRUSH rule pattern for replicated placement (Ceph docs):
```
rule <name> {
   type replicated
   step take <root>
   step choose firstn <N> type <failure-domain-type>
   step chooseleaf firstn <replica-count> type <leaf-domain-type>
   step emit
}
```
For example, `choose firstn 3 type rack` then `chooseleaf firstn 1 type host` places three replicas, one per rack, one host per rack.

Research sources: ceph.com/assets/pdfs/weil-crush-sc06.pdf (CRUSH SC'06 paper), docs.ceph.com CRUSH Maps (reef/latest/mimic), docs.redhat.com CRUSH Administration, libcrush crush.h / python-crush, CACM research highlight on Smash (CRUSH comparison), DeployOpen rack/room failure domains.

#### 3.2 Failure domain hierarchy: power, facility, network, operator, geographic

The five failure-domain dimensions from the prompt map to nested bucket levels:

- **Power domain:** all resources sharing a power source (PDU branch, UPS, circuit, building feed). A rack's PDU trip or UPS failure takes out everything in that power domain. Placement constraint: at most one replica per power domain. (Source: XPC rack power architecture; Moduledge data-center power distribution; US patent US12314571B1 power-diverse replica placement.)
- **Facility domain:** room, building, datacenter — shared cooling, fire suppression, physical access. A fire or flood in a room takes out the whole facility domain. (Source: Ceph CRUSH maps; DeployOpen; Lightbits failure domains.)
- **Network domain:** broadcast domain, top-of-rack switch, VLAN segment, shared uplink. A switch failure or cable cut isolates everything behind it. (Source: OMAda network segmentation; CISA network segmentation; Cyber.gov.au segmentation.)
- **Operator domain:** administrative/operational control boundary — different colo operators, different cloud providers, different organizations managing hardware. Operator error or compromise in one domain should not cascade. (Source: CTS multi-cloud failure domains; Google Cloud building blocks; Oracle resilience independence.)
- **Geographic domain:** region, city, country — independent of network/power/facility. Earthquake, regional power grid failure, jurisdictional action. (Source: AWS AZ fault isolation (60 miles apart, independent power/networking/cooling); Azure availability zones; geo-replication literature.)

Nested relationship: power ⊂ facility ⊂ network ⊂ operator ⊂ geographic (not strictly — domains can cross-cut; e.g., two racks in one facility can be on different power domains and different network segments). The hierarchy is a DAG, not necessarily a tree: CRUSH maps allow a device to appear under multiple buckets (DAG), which `ids-topology` must support for cross-cutting domains (e.g., a host belongs to one rack but could be tagged to multiple operator/jurisdiction labels).

Sources: AWS AZ whitepaper (up to 60 miles apart, independent power/networking/cooling), Azure availability zones overview, Kubernetes topology spread constraints (topology.kubernetes.io/zone, kubernetes.io/hostname), Lethain fault domains (parent level can survive sibling failure), Hadoop rack awareness, Cassandra NetworkTopologyStrategy.

#### 3.3 Correlated failure modeling

The central research finding: assuming independent node failures dramatically overestimates redundancy. With N=3 replicas all in the same rack, a single PDU trip or switch reboot leaves N=1 worth of effective redundancy. Correlated failures (power outages, network component failure) can cause reliability to be overestimated by at least two orders of magnitude (DieHard, CCGrid'16). 

Modeling approach for `ids-topology`:
- Each failure domain carries a failure probability estimate (per-domain, per-time-window).
- A placement set's joint failure probability is computed from the domain membership of each replica: replicas sharing a domain fail together; the probability that ≥ F replicas fail is computed over the domain partition, not the individual nodes.
- **Affinity score** (DieHard): `∑ x_i(x_i − 1)/2` over domain task counts `x_i`; minimized when tasks are spread across domains. Low affinity = low correlated-failure risk.
- Robust vs probabilistic failure-aware placement (SPAA'16 Failure-Aware Placement; ACM TOIT Robust and Probabilistic Failure-Aware Placement): adversarial model (failure budget W over domains) and probabilistic model (per-domain failure probability, minimize P(more than F tasks fail)).
- Sources: CMU-CS-02-129 "On Correlated Failures in Survivable Storage Systems", OSDI'14 "Heading Off Correlated Failures through Independence-as-a-Service", CMU NSDI'06 "Subtleties in Tolerating Correlated Failures", DieHard CCGrid'16, SPAA'16 Failure-Aware Placement, ACM 10.1145/3210367 Robust/Probabilistic Failure-Aware Placement.

#### 3.4 Placement constraints: hard vs soft

- **Hard constraints (must be satisfied or placement fails):** at most one replica per failure domain of type X; minimum number of distinct domains; jurisdiction residency (data must not leave jurisdiction J); power-domain separation; operator separation.
- **Soft objectives (optimized, best-effort):** balance utilization across domains, minimize cross-domain traffic, prefer lower-cost domains, weight by domain reliability.

Research: Application Placement with Constraint Relaxation (arxiv 2507.13895) — hard vs soft constraint priorities; Kubernetes topology spread constraints (maxSkew, minDomains, whenUnsatisfiable: ScheduleAnyway vs DoNotSchedule — hard vs soft); Ceph CRUSH rules (failure domain choice is hard: replication stays degraded if insufficient distinct domains).

#### 3.5 Domain independence verification

Before accepting a placement, verify that the selected domains are actually independent — the CRUSH tree says what it says, but the building decides what actually fails (DeployOpen: "Ceph trusts the CRUSH tree, but the building decides what actually fails"). Checks:
- Two racks sharing one power feed are one power domain, not two.
- Two switches on one uplink are one network domain.
- Bonded links landing on separate switches = genuinely separate network domains.
- Cross-operator claims verified via authenticated topology attestation (ed25519-signed topology updates from each operator).

Independence verification is a separate pass after CRUSH placement: it takes the candidate placement, examines the domain membership edges (shared power, shared network path), and rejects/flags placements where apparent independence is illusory.

#### 3.6 CRUSH vs consistent hashing vs topology-aware scheduling

- **Consistent hashing** (Hadoop, Cassandra ring): gives a preference list but knows nothing about physical adjacency — three consecutive ring nodes can share a rack/power/switch. Needs a separate topology model layered on top.
- **CRUSH**: topology is intrinsic to the map; failure-domain separation is built into the rule language. Preferred for `ids-topology` because the hierarchy is the data structure.
- **Kubernetes topology spread constraints**: declarative spreading across topology keys with maxSkew/minDomains; a good reference for the constraint API shape, but operates at pod-scheduling granularity, not data-placement granularity.

Decision: `ids-topology` uses CRUSH-style hierarchical buckets as its core, with a constraint DSL that can express hard/soft rules per redundancy policy — consistent with `ids-placement-policy` (Phase 053) and `ids-redundancy-mode` (Phase 059).

### 4. Threat Model & Mitigations

|| Threat | Mitigation ||
||--------|-----------|-------------|
| Correlated replicas (all replicas in one power/network domain) | CRUSH hierarchy enforces distinct failure domains per replica; independence verification rejects illusory independence |
| Topology map tampering (attacker claims false independence) | ed25519-signed topology updates per operator/domain; verify signatures before applying map changes |
| Insufficient distinct domains for replica count (placement degraded) | Reject placement with constraint-violation error; never silently place replicas in the same domain (Ceph behavior: degraded until enough domains) |
| Topology staleness (map doesn't reflect real failures) | Versioned topology map with epochs; failed domains marked but left in hierarchy (CRUSH pattern); re-verification on each placement |
| Jurisdiction violation (data placed in forbidden country) | Jurisdiction tags on geographic domains; hard constraint checked before placement |
| Operator collusion / shared backbone | Operator separation constraint; verify no shared backbone between "independent" operators (Oracle resilience independence) |
| Carrier-agnostic boundary violation (std::net/tokio::net leaking) | All topology sync traffic via `ids-carrier::Endpoint`; compile-time dependency audit prohibits std::net/tokio::net/libp2p |

### 7. Key Algorithms & Data Structures

#### 7.1 FailureDomain hierarchy

```
FailureDomain { kind: DomainKind, id: DomainId, weight: u64, tags: Tags, children: Vec<FailureDomain> }
DomainKind ::= Power | Facility | Network | Operator | Geographic | Custom(String)
```

Levels nest: a `NodeId` (leaf) sits under a power domain, which sits under a facility, which sits under a network segment, which sits under an operator, which sits under a geographic region. Cross-cutting tags (jurisdiction, power-feed ID, operator ID) allow DAG membership.

#### 7.2 CRUSH placement (select n distinct items of type t)

```
select(n, t, x):                          // x = input hash (object id)
  result = []
  for r in 0..n:
    item = choose_bucket(x, r, root, t)   // descend hierarchy, pick distinct bucket of type t
    result.push(item)
  return result
```

`choose firstn N type T`: pick N distinct buckets of type T from current bucket's children, retrying on collision (choose_total_tries tunable). `chooseleaf firstn R type T`: recurse into each selected bucket to find one leaf device.

`straw2` bucket choose: for each child, draw = generate_exponential_distribution(hash(x, item_id, r), weight); highest draw wins. Allows optimal data movement on add/remove.

Determinism: same map + same input → same placement, on every node, no coordination.

#### 7.3 Correlated failure probability

Given placement set with domain counts `x = [x_1, ..., x_L]` over L domains:
- Affinity score: `∑ x_i(x_i − 1)/2` — minimized when spread across domains.
- Joint failure probability: `P(≥ F replicas fail) = 1 − P(≤ F−1 fail)` computed over domain failure events (not independent node events).
- Per-domain failure probability `p_i` estimated from observed failures / configured reliability.
- Threshold: placement accepted iff joint failure probability ≤ threshold AND affinity score ≤ max.

#### 7.4 Independence verification

```
verify(candidate_placement, topology_map):
  for each pair of replicas (a, b):
    domains_a = ancestor domains of a (power, facility, network, operator, geographic)
    domains_b = ancestor domains of b
    if shared_power_feed(a, b) or shared_uplink(a, b): FAIL illusory independence
    if not attested_independent(operator(a), operator(b)): FAIL unverified operator separation
    if jurisdiction(a) ∉ allowed or jurisdiction(b) ∉ allowed: FAIL jurisdiction
  return PASS
```

### 10. Remaining Uncertainties

1. **CRUSH bucket algorithm selection:** straw2 (optimal data movement, O(n) choose) vs uniform/list (faster, poor rebalance). Recommend straw2 default (Ceph recommendation).
2. **ids-crypto dependency direction:** ids-crypto does NOT depend on ids-000-aa (avoids cycle), but ids-topology depending on ids-crypto is fine — confirm no transitive cycle via ids-placement etc.
3. **Failure probability source:** per-domain failure probabilities need configuration or observed-failure estimation; estimation method TBD.
4. **Topology map distribution:** how maps are gossiped/synced between nodes (ids-carrier::Endpoint frames) — protocol details deferred to a later phase; this crate owns map structure, not distribution.
5. **DAG vs tree:** cross-cutting domains (jurisdiction overlapping geographic) suggest a DAG; CRUSH supports DAGs but chooseleaf collision handling gets more complex — confirm semantics.
6. **Weight source:** domain weights from capacity (NodeId attributes) — integration with ids-resource (Phase 032) for capacity data TBD.
7. **Independence attestation trust roots:** how operator-signed independence attestations are trusted — ties to ids-identity/bootstrap, TBD.

### 11. Engineering Decisions Summary

|| Decision | Rationale ||
||----------|-----------|-------------|
| CRUSH-style hierarchical buckets as core | Topology intrinsic to map; failure-domain separation built into rule language (Weil et al. SC'06; Ceph) |
| straw2 bucket algorithm default | Optimal data movement on add/remove; Ceph-recommended |
| Distinct failure domains per replica (hard) | A single correlated event must not take out >1 replica (AWS AZ independence, 60 miles apart) |
| Five domain kinds: power, facility, network, operator, geographic | Matches prompt spec and CRATES.md crate #6 contents |
| Independence verification separate from CRUSH placement | "Ceph trusts the CRUSH tree, but the building decides what actually fails" (DeployOpen) |
| Placement fails on insufficient domains, never silently colocates | Ceph behavior: replication stays degraded until enough domains exist |
| Deterministic, directory-free placement | No central directory; matches no-global-master invariant; carrier-agnostic |
| All cross-node traffic via ids-carrier::Endpoint only | Carrier-agnostic absolute rule (no std::net/tokio::net/libp2p/etc.) |
| ed25519 for topology-update signatures; sha256/blake3 for content hashing | Allowed crypto set only |
| Hard vs soft constraint split | Mirrors Kubernetes topology spread constraints (ScheduleAnyway vs DoNotSchedule) and CRUSH rule semantics |
